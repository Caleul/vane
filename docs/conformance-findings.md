## Reproduced product regressions (BUG)

Both were reproduced through an npm-installed `@lilka/vane@0.0.0` tarball on
Node 24.19.0 and real PostgreSQL 16.15, after successfully applying a migration
generated by the same public API. Existing regression tests still pass.

1. **Datetime default rejected at startup** — EE-COL-002,
   `postgres.datetime-default-startup`. A valid datetime Column default
   `2026-09-01T08:00:00.000Z` materializes successfully, but
   `PostgreSqlModuleRuntime.start()` raises
   `PostgreSqlModuleRuntimeConfigurationError`. PostgreSQL canonicalizes the
   timestamp's representation/time zone; startup compares the surviving literal
   text instead of its equivalent timestamp value. The case expects successful
   startup followed by persisted default equality.
2. **Equivalent CHECK column order rejected at startup** — EE-RUL-003,
   `postgres.rule-column-order-startup`. A valid Rule `units <= capacity`
   materializes a PostgreSQL CHECK successfully, but runtime startup rejects it.
   PostgreSQL's CHECK reference list follows expression order, while the compiled
   list is alphabetically canonicalized. Ordered column comparison is necessary
   for some key constraints, but does not establish CHECK-expression equivalence.
   The case expects successful startup and database rejection of a violating row.

The general independent fixture uses an explicit Event datetime value and the
mathematically equivalent Rule `capacity >= units` so unrelated evidence can run.
The original valid declarations remain in separate **failing** cases; they are
not skipped or accepted by a waiver. No production implementation is changed in
this candidate-suite PR.

Reproduce on a disposable PostgreSQL 16+ database:

```sh
npm run build
VANE_CONFORMANCE_DATABASE_URL=postgresql://user:password@localhost:5432/test \
  node conformance/pack-and-run.mjs --id EE-COL-002 --json
VANE_CONFORMANCE_DATABASE_URL=postgresql://user:password@localhost:5432/test \
  node conformance/pack-and-run.mjs --id EE-RUL-003 --json
```

## Remaining evidence and decisions

GAP means missing or partial independent evidence, not automatically a missing
product capability. Each row in the catalog retains its concrete precondition,
action and observable expectation; reports include those reproduction steps.
Do not turn these into PASS by pointing at internal test counts.

The smallest next batches are:

1. Correct the two narrowly reproduced startup comparisons, retaining drift
   rejection and the independent negative cases; rerun packaged conformance and
   the full regression gates.
2. Resolve the scope/API questions behind optional physical Column customization,
   multiple services sharing a physical database, genuinely different profile
   provider/topology choices, and inferred Event-input/View-output TypeScript
   payload types. Record a normative clarification where needed before inventing
   new builders or APIs. Productive distributed execution stays out of v0.1.
3. Close the explicitly listed missing public-boundary/type/representation cases
   and verify generated bootstrap/image/provenance. Reproduce the existing
   Sales/Billing reference and perform the documented public quickstart review;
   this is evidence for the original baseline, not new Phase 8 dogfood projects.
4. Establish and record reproducible measurement conditions for the three
   performance bounds. Safety timeouts in the runner do not count as benchmarks.

No release, package publication, merge, remote deployment, Moto integration or
new general-purpose harness product is part of this change.
